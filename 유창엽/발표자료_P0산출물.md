## 3. 검색·추천 로직 검수 결과

### ✅ 검수 완료 (구현 확인됨)

- **통합검색**: 검색어 → Gemini embedding → Supabase `match_announcements_hybrid` RPC → similarity 기반 후보 추출
- **통합검색 보정**: 지역 exact match +30, 나이 조건 일치 +10 보정 적용
- **통합검색 fallback**: hybrid RPC 실패 시 → basic RPC → `announcements` 테이블 컬럼 보강 3단계 방어
- **조건검색**: 지역/분야는 DB 단계 hard filter, 나이는 공고 연령 조건과 비교 보정
- **조건검색 추천순**: condition_score (지역 30 + 분야 20 + 명시 나이 10), 동점 시 마감 빠른 순
- **스크랩**: 토글/저장/삭제/조회 흐름 완성
- **AI 추천**: 프로필 또는 스크랩 기반 추천 분기 흐름 존재
- **챗봇**: 질문 + 프로필 + 대화 맥락 결합 → pgvector RPC → Gemini 답변
- **챗봇 confirm**: 질문 조건 vs 프로필 조건 충돌 시 사용자 확인 흐름 적용

### ⚠️ 표현 주의 (구현됐지만 정확히 말해야 함)

- **분야 가중치**: 통합검색 final_score에는 **직접 들어가지 않음** (self-query로 추출만 됨)
- **대상 필터**: 대부분 hard filter가 아님 (UI 조건 또는 보조 조건)
- **AI 추천**: 프로필과 스크랩을 항상 둘 다 반영하지 않음 (분리된 흐름)

### ❌ 미구현 (구현된 것처럼 말하면 안 됨)

- **저장 대화 embedding 검색**: `query_embedding` 기반 의미 검색은 없음. transcript 저장만 있음
- **자동 수집 로그 (api_batch_logs)**: yml에 DB 기록 로직 빠짐, 관리자 화면에 안 보임
- **신청 현황 / 조회수 / 전환율 / MAU / 알림**: 미구현
- **관리자 정책 CRUD**: read-only 통계 화면만 존재

### 4-2. 기능별 발표 압축 설명 (3~5문장)

#### 통합검색 (3문장 압축)

> 통합검색은 검색어를 Gemini embedding으로 바꿉니다. 그 embedding을 Supabase pgvector RPC로 보내 공고 embedding과 유사도를 계산합니다. 단순 키워드 포함이 아니라 의미적으로 가까운 공고를 먼저 보여주는 방식입니다.

#### 조건검색 (3문장 압축)

> 조건검색은 사용자가 직접 고른 지역, 분야, 나이 조건으로 후보를 좁힙니다. 지역과 분야는 DB 단계에서 hard filter로 적용되고, 나이는 공고의 연령 조건과 비교 보정됩니다. 추천순은 condition_score로 조건 적합도가 높은 공고가 먼저 오도록 정렬합니다.

#### 정렬 (3문장 압축)

> 정렬은 추천순, 마감순, 신규순 세 가지입니다. 통합검색 추천순은 검색어 의미 유사도가 중심이고, 조건검색 추천순은 조건 적합도가 중심입니다. 마감순과 신규순은 사용자가 목적에 따라 결과를 다르게 볼 수 있도록 추가했습니다.

#### AI 추천 (3문장 압축)

> AI 추천은 로그인 사용자의 저장된 프로필과 최근 스크랩 이력 중 사용 가능한 신호를 활용합니다. 프로필 기반 추천과 스크랩 기반 추천은 분리된 흐름으로, 항상 둘 다 반영되는 것은 아닙니다. 추출된 후보는 조건 일치도와 vector similarity를 함께 참고해 다시 정렬합니다.

#### 챗봇 (4문장 압축)

> 챗봇은 사용자 질문, 프로필 조건, 현재 대화 맥락을 함께 보고 검색용 query를 만듭니다. 같은 Supabase pgvector RPC로 관련 공고를 찾고, 검색된 공고 내용을 근거로 Gemini가 답변을 생성합니다. 프로필 조건과 질문 조건이 충돌할 수 있을 때는 사용자 확인을 거치는 흐름을 두었습니다. 저장 대화는 transcript로 남지만 embedding 의미 검색까지 구현된 것은 아닙니다.

#### 스크랩 (3문장 압축)

> 스크랩은 사용자가 관심 공고를 저장해 나중에 다시 볼 수 있게 하는 기능입니다. 공고 카드에서 스크랩 버튼을 누르면 `/api/mypage/scraps`로 사용자별 데이터가 저장/삭제됩니다. 스크랩은 단순 저장에 그치지 않고, 이후 추천 후보를 만들 때 관심 이력의 신호로 다시 활용됩니다.

## 7. HEAD vs 로컬 차이 (발표자 알림용)

발표 당일 데모 환경 명확히 정해야 함.

### GitHub HEAD 기준 (`b40ec73 chore: 사용자 화면 정리`)

- 검색어 있는 마감순/신규순: 받아온 10개 결과 안에서 클라이언트 정렬
- 검색어 관련 후보 충분치 않으면 날짜 정렬 데모 흔들릴 수 있음

### 로컬 데모 기준 (창엽님 보강 버전)

- 검색어 있는 날짜 정렬도 서버에 `sort_by` 전달
- 서버에서 후보 50개 확보 → 관련도 floor → 날짜 정렬
- 전세사기/창업 키워드 보조 컷 추가
- 데모 품질 더 안정적

### 권장 사항

발표 직전 로컬 보강 버전을 push해서 GitHub과 동기화하는 것을 추천. 그렇지 않으면 발표용 환경(로컬 빌드)과 GitHub 코드가 어긋남.

## 8. 슬라이드 13 (어려웠던 점) - 검색/추천 영역 P1

### 8-1. 어려움 1: 검색어·UI 필터·프로필 조건의 우선순위 정리

> **핵심 문장**: "사용자가 문장으로 검색할 수도 있고, 필터를 직접 고를 수도 있고, 프로필 조건이 저장돼 있을 수도 있어서, 이 세 가지가 동시에 들어왔을 때 어느 것을 우선할지 정리하는 일이 어려웠습니다."

**왜 어려웠나**: 검색어 의미 유사도, UI 필터 hard filter, 프로필 보조 조건이 충돌할 수 있음. 예: 프로필은 서울인데 검색어가 "부산"이면 어느 쪽을 우선할지 결정해야 함.

**어떻게 해결했나**: 통합검색은 검색어 의미 유사도 중심으로, 조건검색은 UI 필터 적합도 중심으로 흐름을 분리. 챗봇은 충돌 시 사용자 확인(confirm) 흐름을 추가.

---

### 8-2. 어려움 2: 추천순·마감순·신규순의 의미 구분

> **핵심 문장**: "정렬이 같은 검색 결과라도 사용자 입장에서 다르게 보여야 의미가 있어서, 추천순·마감순·신규순이 각각 어떻게 다른지 화면 동작과 정렬 기준을 정리하는 일이 어려웠습니다."

**왜 어려웠나**: 통합검색 추천순은 의미 유사도 중심, 조건검색 추천순은 조건 적합도 중심. 둘이 같은 추천순이지만 내부 로직이 다름. 마감순은 검색 결과 후보를 어떻게 가져오느냐에 따라 품질이 흔들림.

**어떻게 해결했나**: 통합검색과 조건검색의 추천순 점수 산정을 분리. 마감순/신규순은 서버에서 충분한 후보를 가져온 뒤 정렬하도록 로컬 버전에서 보강.

---

## 9. 슬라이드 14 (한계와 개선 방향) - 검색/추천 영역 P1

### 9-1. 한계

- **대상 필터 hard filter 한계**: UI에는 대상 필터가 있지만 대부분 hard filter가 아닌 보조 조건. 원본 데이터의 대상 조건이 자유 텍스트이거나 출처별 표현이 달라 정규화가 어려움.
- **통합검색 분야 가점 미적용**: 검색어에서 분야가 추출돼도 통합검색 final_score에 직접 반영되지는 않음. 후보 누락 방지를 위해 일부러 hard filter로 쓰지 않았음.
- **검색어 있는 날짜 정렬 한계**: HEAD 기준에서는 상위 10개 안에서만 날짜 정렬돼 데모 품질이 흔들릴 수 있음. 로컬 보강 버전에서만 후보 확장이 적용됨.
- **저장 대화 의미 검색 미구현**: `chat_history`에 transcript 저장은 가능하지만, 저장 대화를 embedding으로 의미 검색해 답변에 활용하는 구조는 아직 없음.

### 9-2. 향후 개선 방향

- **대상 표준 태그 정규화**: 대상 조건을 표준 태그로 정규화하고, 대상별 hard filter 컬럼을 추가.
- **self-query category soft boost**: 검색어에서 추출한 분야를 soft boost로 반영하되, 후보 누락을 막는 threshold를 함께 설계.
- **검색어 있는 정렬 통일**: 모든 정렬 모드에서 서버가 충분한 후보를 가져온 뒤 정렬하도록 통일.
- **대화 요약 embedding**: 대화 요약 embedding을 별도 저장하고, 사용자 동의 범위에서 의미 검색 추가.

### 9-3. 발표용 압축 멘트 (2문장)

> "현재는 MVP 단계라 대상 필터 정규화, 분야 가점 반영, 저장 대화 의미 검색 같은 부분이 더 다듬어질 수 있습니다. 향후에는 검색어와 조건이 더 자연스럽게 결합되는 통합 정렬 흐름, 대상별 hard filter 컬럼, 사용자 동의 기반 대화 의미 검색까지 확장할 수 있습니다."

## 10. 이미지 2 확인 포인트 답변

작업분담안 섹션 5에서 너에게 요구한 확인 포인트 4가지에 대한 답변.

### 확인 포인트 1: `web/app/api/search/route.ts`가 통합검색과 조건검색 모두 담당하는 설명이 맞는지

✅ **맞음**. 단일 API Route(`/api/search`)가 검색어 유무, 필터 조건, 정렬 옵션을 모두 받아서 처리. 검색어가 있으면 embedding 흐름, 없으면 필터 only 흐름으로 분기.

### 확인 포인트 2: `web/app/api/mypage/recommendations/route.ts`의 추천 신호를 발표용으로 단순화해도 되는지

✅ **가능**. 발표에서는 "프로필 조건 + 스크랩 이력 → 추천 후보 → 유사도/조건 일치도로 정렬" 정도로 단순화. 세부 가중치 수치(40%/30%/20%/10%)는 발표에서 강조하지 않음.

### 확인 포인트 3: `web/app/api/chat/rag/route.ts` 설명이 현재 MVP 범위를 넘지 않는지

⚠️ **주의 필요**. "질문 + 프로필 + 대화 맥락" 흐름까지만 설명 OK. "저장 대화 의미 검색", "장기 기억" 같은 표현은 미구현 영역이라 피해야 함.

### 확인 포인트 4: 데모에서 챗봇 추천이 불안정하면 맞춤 추천 중심으로 바꾸고 챗봇은 "가능한 흐름" 정도로만 언급

✅ **반영 완료**. 섹션 1의 "챗봇 불안정 시 대체안 (Plan B)" 참조. 챗봇 응답 흔들리면 맞춤 추천 카드 시연으로 전환하는 흐름 정리됨.
