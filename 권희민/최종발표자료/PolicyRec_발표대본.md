## 6. 통합검색 시연

먼저 통합검색입니다.

여기서는 검색창에
**“청년 자산형성 저축 지원”**을 입력해보겠습니다.

정책명을 정확히 몰라도 청년, 자산형성, 저축, 지원처럼
상황 키워드를 조합해 탐색을 시작하는 흐름입니다.

검색 결과를 보면 청년 자산형성이나 저축 지원과 관련된 공고들이 카드 형태로 나타납니다.

같은 검색 결과 안에서 추천순, 마감순, 신규순을 짧게 바꿔보겠습니다.
추천순은 관련성이 높은 공고를 먼저 보고,
마감순과 신규순은 일정 기준으로 같은 후보를 다시 확인하는 흐름입니다.

> 발표자 메모: 비슷한 이름의 공고가 같이 보일 수 있는데, 중앙부처 사업을 지자체가 지역별로 안내하는 경우가 있어 기관·지역·상세 URL이 다르면 정보 손실을 막기 위해 별도 공고로 유지했습니다.


## 7. 검색 결과 카드

검색 결과 카드는 공고를 빠르게 비교할 수 있도록 구성했습니다.

카드에서는 기본적으로
제목, 기관, 지역, 분야, 모집상태, 마감일을 
먼저 보여주고 있고요.

더보기를 누르면 요약이나 신청 방법처럼
API에서 제공되는 추가 정보도 확인할 수 있습니다.

더보기란은 조금씩 차이가 있는데
모든 API가 같은 수준의 상세 정보를 제공하는 것은 아니기 때문에,  
값이 없는 항목은 무리하게 표시하지 않고   
실제로 확인 가능한 정보만 보여주도록 정리했습니다.  

또 제목이나 공고보기 버튼을 누르면   
API로 연결된 페이지로 이동합니다.

폴리시렉 PolicyRec은 신청 자체를 대신하기보다는,
사용자가 관심 공고를 빠르게 발견하고
공식 원문으로 연결될 수 있도록 구성했습니다.

> 발표자 메모: 신청 대행까지 넣지 않은 이유를 묻는다면, 기관별 접수 절차와 자격 확인은 공식 원문에서 처리하는 편이 더 안전하다고 답변합니다.



## 7-2. 문장형

이번에는 키워드가 아니라 문장으로 검색해보겠습니다.

예를 들어 **“부산에서 전세피해 지원받을 수 있을까?”**라고 입력해보겠습니다.

이렇게 정확한 정책명이나 키워드를 몰라도
지역과 상황이 담긴 문장만으로
탐색을 시작할 수 있습니다.

검색 결과에서는 부산 전세피해와 관련된 주거 지원 공고를 확인할 수 있습니다.


## 8. 챗봇 시연

이어서 챗봇으로 진행해보겠습니다.

통합검색이 관련 공고를 찾아주는 기능이라면,
챗봇은 검색된 공고를 바탕으로
사용자가 먼저 확인해야 할 조건이나 주의사항을
대화형으로 정리해주는 기능입니다.

> “부산에서 전세피해 지원받을 수 있을까?
> “부산 전세피해 지원 공고 중에서 내가 먼저 확인해야 할 내용을 정리해줘”

그러면 전세사기피해자 결정 여부처럼
신청 전에 먼저 확인해야 할 핵심 조건과,
사업별 주의사항을 정리해주는 것을 확인할 수 있습니다.

챗봇은 단순 생성형 답변을 하는 것이 아니라,
저희 DB의 관련 공고를 근거로 답변하도록 구성했습니다.

> 발표자 메모: 챗봇 답변 본문은 전세피해 관련 사업을 중심으로 정리되지만, 아래 후보 카드에는 부산 주거 관련 공고가 일부 함께 보일 수 있습니다. 이 경우 RAG가 후보를 넓게 가져온 뒤 답변 본문에서 질문과 관련 있는 내용을 우선 정리하는 구조라고 설명합니다.

그리고 로그인을 하면 나눈 대화는 message 탭에 저장되고,
다시 대화를 이어갈 수도 있습니다.

## 10. 정렬 시연

조건검색 결과에서도
사용자가 중요하게 보는 기준은 다를 수 있죠.

그래서 결과는 마감순(마감 가까운순), 신규순(새로올라온순), 추천순으로 정렬할 수 있도록 했고요.

추천순은 조건과 관련성이 높은 공고를 먼저 보여주고,
마감, 신규순은 말 그대로 공고 마감일이 가까운 순과 
신규등록 날짜순으로 정렬을 보여줍니다.

(그리고 조건이 이미 강하게 좁혀진 경우에는
추천순과 마감순 결과가 일부 비슷하게 보일 수 있습니다.

그래도 사용자가 확인하고 싶은 기준에 따라
결과를 바꿔볼 수 있도록 정렬 기준을 제공했습니다.)

## 13. 마이페이지 정보설정과 AI 추천공고

마이페이지에서는 사용자가 프로필 조건을 저장할 수 있는데요.
나이, 지역, 유형, 관심 분야를 설정하고 또 수정할 수 있습니다.

저장된 프로필 조건과 최근 관심 이력을 참고해
메인 화면에서는 관련 공고를
AI 추천공고 형태로 보여주고 있고요.

이렇게 조건을 설정해두면
메인의 AI 추천공고에서
사용자가 매번 직접 검색하지 않아도,
내 조건과 최근 관심 흐름에 가까운 공고를
먼저 확인할 수 있도록 구성했습니다.

현재는 저장된 프로필 조건과 최근 관심 이력을 참고해
관련 공고를 우선 보여주는 방식으로 구현했습니다.

> 발표자 메모: AI 추천공고는 완전한 개인화 학습 모델은 아니고, 이번 프로젝트 범위에서는 조건과 관심 이력을 신호로 활용한 추천 방식입니다.



## 14. 관리자 조회 화면

마지막으로 보여드릴 웹 화면은  

관리자 조회 화면입니다.  

정책을 추가하거나 수정하는 CMS는 아니고,
실제 DB 상태를 확인하는 읽기 전용 관리자 화면으로 구성했고요.

> 발표자 메모: 관리자 화면은 정책을 직접 편집하는 CMS가 아니라, DB 상태를 확인하는 읽기 전용 조회 화면입니다.
> 발표자 메모: CMS(conent management system) 콘텐츠 관리 시스템으로, 정책을 직접 등록·수정하는 프로그램



정책 서비스는 데이터 품질이 중요하기 때문에   

관리자가 현재 DB에 어떤 공고가 있고,   

분야와 지역 분포가 어떻게 되어 있는지,  

또 회원들이 어떤 공고에 관심있어 하는지 등등을

빠르게 확인할 수 있는 조회 화면으로 만들었습니다.   

사용자 현황에서는 이렇게 가입자 정보도 간단하게 확인할 수 있습니다.



## 15. 서비스 뒤의 데이터 흐름

지금까지 웹 화면에서 구현된 서비스를 보여드렸는데요

> 발표자 메모: 슬라이드 15p로 이동합니다.

이제는 서비스 뒤에 데이터 흐름을 살펴보겠습니다.

3개 API 데이터를 수집한 뒤, 서비스에서 공통으로 사용할 수 있는 구조로 정리했습니다. 

이후 검색을 위해 임베딩을 만들고, main CSV 기준으로 정리한 데이터를 Supabase에 벡터 DB로 저장해서

Next.js 화면과 API Route에서 조회할 수 있도록 연결했습니다.

이 구조가 통합검색, 조건검색, AI 추천, 챗봇 응답으로 이어집니다.

## 17. EDA

EDA에서는 세 API의 원천 데이터 구조가   
어떻게 다른지 먼저 확인했습니다.

기업마당은 22개,    
K-Startup은 30개,   
온통청년은 60개 컬럼으로    
총 112개 원본 컬럼이 있었습니다.

이렇게 예시를 몇개 가져와봤는데,
컬럼명, 주관 기관, 지원 대상, 신청기간, 지역 등 컬럼명이 달라서    
단순히 이어붙이는 방식으로는 검색과 필터에 쓰기 어려웠습니다.


## 18. 전처리와 공통 컬럼화
> ⭐
그래서 112개 원천 컬럼을   
검색과 추천에 필요한 29개 공통 컬럼으로 정리했습니다.

raw 데이터는 날짜·지역·분야 표현을 표준화하고
중복 여부를 확인해서 
서비스에서 사용하는 main CSV 기준으로 정리했고요.

그 결과 약 600건의 원천 데이터를 
최종 565건의 서비스용 공고 데이터로 만들었습니다.

다만 이름이 비슷한 공고라도   
기관이나 지역, 상세 링크가 다르면   
사용자가 확인해야 할 정보가 달라질 수 있어서    
이런 경우는 무리하게 합치지 않고 별도 공고로 유지했습니다.

## 19. rule표

공통 컬럼으로 맞춘 뒤에는,   
실제 값의 표현도 서비스 기준으로 통일했습니다.   

API마다 지역, 분야, 대상, 지원 범위 표현이 달랐기 때문에   
rule표를 이용해 같은 의미의 값은 같은 기준으로 매핑했습니다.   

예를 들어 서울, 서울특별시, [서울]은 서울특별시로,   
창업, 창업지원 처럼 비슷한 분야 표현은 서비스 기준의 분야값으로 정리했습니다.   

이 공통 기준을 바탕으로 검색, 조건검색, 추천, 챗봇이   
같은 데이터 기준에서 동작하도록 구성했습니다.   




## 20. 검색과 추천 로직

검색과 추천은 같은 공고 데이터를 사용하지만,   
사용자가 어떤 방식으로 들어오느냐에 따라      
다르게 동작하도록 나눴습니다.   
   
통합검색은 사용자가 입력한 키워드나 문장을 임베딩으로 바꿔서,   
공고 내용과 의미가 가까운 결과를 찾는 방식입니다.   
여기에 지역이나 나이처럼 관련성 판단에 도움이 되는 단서가 있으면   
후보를 좁히거나 보조 점수로 반영했습니다.   

조건검색은 사용자가 직접 선택한 지역과 분야를 기준으로   
DB 조회 단계에서 후보를 먼저 좁히는 방식입니다.   
모집상태는 시작일과 마감일을 기준으로 계산해서 화면에서 필터링하고,   
나이는 필수 입력값이 아니라 선택값으로 두었습니다.   
나이를 입력한 경우에만 공고의 연령 조건과 비교하고,   
대상에서 청년을 선택하면 청년 연령대가 보조 조건으로 함께 전달됩니다.   

맞춤 추천은 저장된 프로필 조건과   
최근 관심 이력 중 사용할 수 있는 신호를 참고해   
관련 공고를 우선 보여주는 방식입니다.   

챗봇은 저희 DB의 관련 공고를 근거로,   
사용자가 먼저 확인해야 할 조건과 주의사항을   
Gemini가 답변으로 정리하고,   
대화 형식으로 이어갈 수 있도록 구성했습니다.   



## 21. 프로그램 구조

위에는 전체 프로그램 구조이고,
아래는 기능별 요청 흐름 예시입니다.

저희는 역할을
Next.js 화면, API Route, Supabase, Gemini로 나누어 구현했습니다.

Next.js는 사용자가 보는 웹 화면을 담당하고,

API Route는 검색, 추천, 스크랩, 챗봇 등의 요청을 처리하는 중간 역할을 합니다.

Supabase는 데이터, 사용자 정보, 스크랩 내역, 챗봇 이력 같은
실제 데이터를 저장하고 관리합니다.

Gemini는 모든 기능에 쓰이는 것이 아니라,
검색용 embedding 생성과 챗봇 답변 생성에 사용했습니다.


아래에는 스크랩과 챗봇 요청 흐름을 예시로 정리했습니다.

먼저 스크랩은 사용자가 별표 버튼을 누르면
API Route를 거쳐 Supabase에 저장됩니다.

그리고 챗봇은 사용자가 질문을 입력하면
API Route가 요청을 처리하고,
Supabase에서 관련 공고를 먼저 찾은 뒤
그 결과를 바탕으로 Gemini가 답변을 생성합니다.


## 22. 어려웠던 점과 해결 방식


저희가 이 서비스를 개발하면서 어려웠던 점은
기능을 많이 만드는 것보다,
서로 다른 데이터를 같은 기준으로 정리하는 일이었습니다.

API마다 컬럼명, 날짜 형식, 지역과 분야 표현이 달라서
rule표를 기준으로 공통 컬럼과 분류 기준을 맞췄습니다.

> 🖰⭐
또 검색 기준도 기능별로 달랐습니다.
통합검색은 의미가 가까운 공고를 넓게 찾는 것이 중요했고,
조건검색은 사용자가 선택한 지역이나 분야를 정확히 지키는 것이 중요했습니다.
추천은 저장된 프로필과 관심 이력을 보고,
챗봇은 현재 질문에 맞는 공고를 찾아 설명하는 역할이었습니다.

그래서 네 기능을 하나의 점수 로직으로 섞기보다는
통합검색, 조건검색, 추천, 챗봇을 각각 다른 기준으로 분리했습니다.

> 🖰⭐
마지막으로 비슷한 공고가 여러 개 보이는 문제도 있었습니다.
중앙부처 정책을 지자체가 다시 안내하는 경우처럼,
이름은 비슷해도 기관, 지역, 접수 경로가 다를 수 있기 때문입니다.

현재는 정보 손실을 막기 위해 별도 공고로 유지했고,
향후에는 유사 공고를 묶어서 보여주는 방식으로 개선할 수 있을 것 같습니다.
