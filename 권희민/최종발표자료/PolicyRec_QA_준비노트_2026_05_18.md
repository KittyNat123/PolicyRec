# PolicyRec Q&A 준비노트 (2026-05-18)

## 1. 답변 원칙

- 과장하지 않기
- MVP 범위와 한계는 솔직하게 말하기
- 최종 신청/자격 판정은 공식 원문 공고 확인으로 연결하기
- 답변은 “직접 답변 → 구현 방식 → 한계/개선점 → 사용자 의미” 흐름으로 정리하기

안전한 시작 문장:

현재 MVP에서는 그 부분을 완전히 자동화하거나 고도화한 단계라기보다는, 사용자가 흩어진 정책 공고를 한곳에서 찾고 내 조건에 맞게 좁혀볼 수 있는 흐름을 구현하는 데 집중했습니다.

## 2. 필수 예상 질문

### Q. 기존 정책 사이트와 차별점이 뭔가요?

**바로 말할 답변**

기존 정책 사이트는 공고를 각각 찾아보는 방식에 가깝다면, PolicyRec은 여러 공식 API의 공고를 한곳에 모으고 사용자가 자기 상황에 맞게 탐색할 수 있도록 흐름을 만든 점이 차별점입니다. 통합검색, 조건검색, 스크랩, 추천, 챗봇을 하나의 서비스 안에서 연결해서, 사용자가 흩어진 공고를 더 쉽게 찾고 내 조건에 맞게 좁혀볼 수 있게 했습니다.

**더 짧게 말하면**

여러 공식 API 공고를 한곳에 모으고, 검색부터 추천과 챗봇까지 이어지는 탐색 흐름을 만든 것이 차별점입니다.

**주의할 표현**

“기존 사이트보다 완전히 낫다”, “모든 정책을 다 포함했다”처럼 단정하지 않기.

### Q. API 3개를 어떻게 통합했나요?

**바로 말할 답변**

온통청년, 기업마당, K-Startup은 컬럼명, 날짜 형식, 지역과 분야 표현 방식이 서로 달랐습니다. 그래서 제목, 기관, 요약, 지역, 분야, 모집기간, 지원대상, 신청방법, 상세 URL처럼 서비스에서 공통으로 필요한 값을 기준으로 컬럼을 맞췄습니다. 이렇게 정리한 데이터를 검색, 조건검색, 추천, 챗봇이 함께 사용할 수 있게 만든 것이 핵심입니다.

**더 짧게 말하면**

서로 다른 3개 API의 원본 구조를 공통 컬럼으로 맞추고, 같은 데이터가 여러 기능에서 쓰이도록 정리했습니다.

**주의할 표현**

“API 데이터를 그대로 합쳤다”라고 말하지 않기. 표준화와 매핑 과정이 있었다고 설명하기.

### Q. 112개 컬럼을 왜 29개로 줄였나요?

**바로 말할 답변**

원본 API에는 서비스 화면이나 검색에 바로 쓰기 어려운 컬럼도 많았습니다. 그래서 카드 표시, 검색, 조건 필터, 추천, 원문 연결에 필요한 항목을 중심으로 29개 공통 컬럼을 정했습니다. 원본 정보를 무작정 버린 것이 아니라, 요약, 지원내용, 신청방법, 제출서류, 추가조건처럼 서비스에서 의미 있게 보여줄 수 있는 필드로 최대한 매핑했습니다.

**더 짧게 말하면**

서비스에 필요한 핵심 정보만 공통 구조로 정리한 것이고, 의미 있는 원본 정보는 가능한 공통 필드에 옮겼습니다.

**주의할 표현**

“불필요한 컬럼을 전부 삭제했다”라고 말하지 않기. “서비스용 공통 컬럼으로 정리했다”라고 말하기.

### Q. 600건에서 565건이면 중복 제거가 많이 된 건 아닌가요?

**바로 말할 답변**

맞습니다. 565건은 중복 제거만으로 줄어든 결과라기보다, 중복 제거와 날짜, 지역, 분야 표준화를 거쳐 최종 서비스용 데이터로 정리한 결과입니다. 정책 공고는 이름이 비슷해도 기관, 지역, 접수 경로가 다르면 사용자가 확인해야 할 정보가 달라질 수 있습니다. 그래서 완전 중복이나 처리하기 어려운 데이터는 줄였지만, 정보 손실을 막기 위해 유사 공고는 일부 별도 공고로 유지했습니다.

**더 짧게 말하면**

단순 중복 삭제가 아니라 표준화까지 포함한 정리 결과이고, 기관이나 지역이 다른 유사 공고는 정보 손실을 막기 위해 남겼습니다.

**주의할 표현**

“중복을 모두 제거했다”라고 말하지 않기. 유사 공고와 완전 중복을 구분했다고 설명하기.

### Q. 통합검색과 조건검색은 뭐가 다른가요?

**바로 말할 답변**

통합검색은 사용자가 키워드나 문장을 입력해서 넓게 탐색하는 기능입니다. 반면 조건검색은 지역, 분야, 모집상태, 나이처럼 사용자가 알고 있는 조건을 직접 선택해 후보를 좁히는 기능입니다. 처음에는 통합검색으로 넓게 찾고, 더 구체적인 기준이 있을 때 조건검색으로 줄여볼 수 있도록 나눴습니다.

**더 짧게 말하면**

통합검색은 문장이나 키워드로 넓게 찾는 기능이고, 조건검색은 선택한 조건으로 후보를 좁히는 기능입니다.

**주의할 표현**

“둘이 같은 검색인데 UI만 다르다”라고 말하지 않기. 탐색 목적이 다르다고 설명하기.

### Q. 검색, 조건검색, 추천, 챗봇을 왜 굳이 나눴나요?

**바로 말할 답변**

같은 공고 데이터를 쓰더라도 사용자가 찾는 방식은 다를 수 있기 때문입니다. 통합검색은 모르는 정책을 넓게 찾는 기능이고, 조건검색은 알고 있는 조건으로 좁히는 기능입니다. 추천은 사용자가 직접 검색하지 않아도 프로필 조건과 관심 이력을 참고해 후보를 먼저 보여주는 기능이고, 챗봇은 여러 공고의 핵심 내용을 이해하기 쉽게 정리해주는 역할입니다.

**더 짧게 말하면**

각 기능은 같은 데이터를 쓰지만, 찾기, 좁히기, 먼저 보여주기, 쉽게 설명하기라는 역할이 다릅니다.

**주의할 표현**

“기능을 많이 넣기 위해 나눴다”라고 말하지 않기. 사용자 탐색 방식이 달라서 나눴다고 답하기.

### Q. 추천순은 어떤 기준인가요?

**바로 말할 답변**

추천순은 완성형 개인화 추천 모델이라기보다는, 현재 질문이나 선택한 조건과 더 관련 있는 공고를 위로 보여주기 위한 정렬 기준입니다. 통합검색에서는 검색어와 공고 내용의 의미적 관련도를 보고, 조건검색에서는 지역, 분야, 모집상태, 입력된 나이 같은 조건 일치도를 함께 봅니다. 다만 이것이 신청 가능 여부를 판정하는 것은 아니고, 사용자가 관련 공고를 더 빨리 찾도록 돕는 보조 기준입니다.

**더 짧게 말하면**

추천순은 검색어와 조건에 더 가까운 공고를 먼저 보여주는 관련도 우선 정렬입니다.

**주의할 표현**

“AI가 신청 가능성을 정확히 판단한다”라고 말하지 않기. 관련도 정렬이라고 말하기.

### Q. AI 추천공고는 실제로 어떤 방식인가요?

**바로 말할 답변**

AI 추천공고는 완전한 개인화 학습 모델은 아닙니다. 현재 MVP에서는 저장된 프로필 조건과 최근 관심 이력 중 활용 가능한 신호를 참고해 관련 공고를 우선 보여주는 방식입니다. 사용자가 매번 검색어를 입력하지 않아도, 내 조건과 가까운 공고를 먼저 확인할 수 있게 하는 데 초점을 뒀습니다.

**더 짧게 말하면**

저장된 프로필 조건과 최근 관심 이력을 참고해 관련 공고를 우선 보여주는 방식입니다.

**주의할 표현**

“완전한 개인화 추천”, “사용자 취향을 학습한다”라고 말하지 않기.

### Q. AI 추천공고와 챗봇 추천은 뭐가 다른가요?

**바로 말할 답변**

AI 추천공고는 메인 화면에서 조건과 관심 이력을 참고해 볼 만한 공고를 카드 형태로 먼저 보여주는 기능입니다. 챗봇 추천은 사용자가 질문을 입력하면 관련 공고를 찾고, 그 공고들의 조건이나 신청 전 확인할 부분을 대화형으로 풀어 설명하는 기능입니다. 그래서 AI 추천공고는 “먼저 보여주기”, 챗봇은 “질문에 맞춰 설명하기”에 가깝습니다.

**더 짧게 말하면**

AI 추천공고는 카드로 먼저 보여주는 기능이고, 챗봇은 질문에 맞춰 공고 내용을 설명해주는 기능입니다.

**주의할 표현**

두 기능이 같은 추천 알고리즘이라고 말하지 않기.

### Q. 통합검색과 챗봇은 뭐가 다른가요?

**바로 말할 답변**

통합검색은 관련 공고를 찾는 기능이고, 챗봇은 검색된 공고를 바탕으로 사용자가 먼저 확인해야 할 조건과 주의사항을 정리해주는 기능입니다. 그래서 통합검색은 결과 목록을 비교하는 데 적합하고, 챗봇은 여러 공고를 읽기 전에 핵심을 이해하는 데 도움이 됩니다. 같은 데이터셋을 쓰더라도 후보를 가져오는 방식과 정렬 기준이 달라 결과 순서가 일부 다를 수 있습니다.

**더 짧게 말하면**

통합검색은 “찾기”, 챗봇은 “찾은 내용을 이해하기 쉽게 정리하기”에 가깝습니다.

**주의할 표현**

“통합검색 결과와 챗봇 결과가 항상 같다”라고 말하지 않기.

### Q. 챗봇 답변은 얼마나 신뢰할 수 있나요? DB에 없는 것도 말하나요?

**바로 말할 답변**

챗봇은 완전히 자유롭게 일반 지식만으로 답하는 방식이 아니라, 먼저 저희 DB에서 관련 공고를 검색하고 그 결과를 근거로 답변하도록 구성했습니다. 다만 챗봇 답변만으로 최종 신청 가능 여부를 판단하는 것은 위험하기 때문에, 세부 조건과 최종 신청은 공식 원문 공고에서 확인하도록 연결합니다. MVP에서는 공고 내용을 쉽게 이해하도록 돕는 역할에 집중했습니다.

**더 짧게 말하면**

챗봇은 검색된 공고를 근거로 설명하지만, 최종 자격과 신청 조건은 원문 공고에서 확인해야 합니다.

**주의할 표현**

“챗봇이 항상 정확하다”, “DB에 없는 내용은 절대 말하지 않는다”처럼 단정하지 않기.

### Q. 신청까지 가능한가요?

**바로 말할 답변**

현재 MVP에서는 신청을 직접 처리하지 않습니다. 정책 신청은 기관별 절차와 자격 확인이 중요하기 때문에, PolicyRec에서는 관련 공고를 찾고 공식 원문 공고로 이동할 수 있게 연결하는 데 집중했습니다. 사용자는 흩어진 공고를 더 쉽게 찾고, 실제 신청은 가장 안전한 공식 경로에서 진행할 수 있습니다.

**더 짧게 말하면**

신청 대행은 하지 않고, 관련 공고를 찾은 뒤 공식 원문 공고로 안전하게 연결합니다.

**주의할 표현**

“자동 신청”, “신청 가능 여부 자동 판정”이라고 말하지 않기.

### Q. 데이터가 최신인가요? 왜 자동 수집을 수요일로 설정했나요?

**바로 말할 답변**

자동 수집을 위한 GitHub Actions yml 구조는 준비되어 있고, 현재는 매주 수요일 실행으로 설정해두었습니다. 다만 발표와 시연 기준으로는 실시간 최신 데이터라고 말하기보다, 검수된 안정 버전 데이터를 기준으로 설명하는 것이 안전합니다. 수요일로 둔 이유는 수집 후 중복, 누락, 날짜 파싱 오류를 주중에 확인하고 수정할 시간을 확보하기 위해서입니다.

**더 짧게 말하면**

자동 수집 구조는 준비되어 있지만, MVP에서는 실시간성보다 안정적인 검수와 반영을 우선했고 수요일은 그 시간을 확보하기 위한 설정입니다.

**주의할 표현**

“항상 실시간 최신입니다”, “매일 자동 업데이트됩니다”라고 말하지 않기.

### Q. 검색 정확도는 어떻게 확인했나요?

**바로 말할 답변**

검색 정확도는 데모 쿼리와 회귀 테스트 성격의 확인을 통해 점검했습니다. 예를 들어 청년 자산형성, 전세피해, 지역 기반 조건검색처럼 실제 시연에 쓸 질문을 넣고 상위 결과가 질문 의도와 맞는지, 추천순과 마감순, 신규순으로 바꿨을 때 관련 없는 공고가 과하게 섞이지 않는지 확인했습니다. 아직 정량 평가가 완전히 고도화된 단계는 아니지만, 발표 시연에서는 안정적인 질의를 기준으로 검증했습니다.

**더 짧게 말하면**

시연 쿼리 기준으로 상위 결과의 관련성과 정렬 전환 시 이상 여부를 직접 확인했습니다.

**주의할 표현**

“검색 정확도를 완전히 검증했다”라고 말하지 않기.

### Q. 가장 어려웠던 점과 향후 개선점은 무엇인가요?

**바로 말할 답변**

가장 어려웠던 점은 서로 다른 API 구조를 하나의 서비스 흐름에서 일관되게 쓰이도록 맞추는 것이었습니다. 단순히 데이터를 모으는 것보다, 그 데이터를 검색, 조건검색, 추천, 챗봇에서 자연스럽게 연결하는 부분이 중요했습니다. 향후에는 자동 수집 안정화, 추천 기준 고도화, 챗봇 답변 근거 표시, 사용자 행동 이력 기반 추천 개선을 보강하고 싶습니다.

**더 짧게 말하면**

가장 어려웠던 점은 서로 다른 데이터를 공통 구조로 맞추는 것이었고, 앞으로는 자동 수집과 추천, 챗봇 근거 표시를 더 보강할 계획입니다.

**주의할 표현**

“이미 운영 서비스 수준으로 완성됐다”라고 말하지 않기.

## 3. 기술 질문 보충

### Q. scope_rule은 무엇인가요?

**바로 말할 답변**

scope_rule은 지역이나 분야처럼 값을 보기 좋게 바꾸는 규칙이라기보다는, 검색과 추천에서 중심으로 볼 공고와 보조성 항목을 구분하기 위한 보정 기준에 가깝습니다. 예를 들어 참여위원회나 정책협의체처럼 일반 지원 공고와 성격이 다른 항목은 other로 두고, 주요 제외 기준에 걸리지 않는 공고는 main으로 두어 검색과 추천에 활용했습니다. 공고를 무조건 많이 보여주기보다, 사용자가 실제로 확인할 만한 공고를 더 잘 찾게 하기 위한 전처리 기준입니다.

**더 짧게 말하면**

scope_rule은 검색과 추천에서 중심 공고와 보조성 항목을 구분하기 위한 전처리 기준입니다.

**주의할 표현**

“값을 단순히 보기 좋게 바꾼 규칙입니다”, “other는 버린 데이터입니다”라고 말하지 않기.

### Q. 개인정보는 어떻게 쓰이나요?

**바로 말할 답변**

현재 MVP에서는 추천과 탐색에 필요한 최소한의 정보, 예를 들어 나이, 관심 지역, 관심 분야, 유형, 스크랩 이력 같은 신호를 사용합니다. 이 정보는 사용자의 조건과 가까운 공고를 우선 보여주기 위한 용도입니다. 향후에는 개인정보 안내와 설정 관리, 추천에 쓰인 기준 설명을 더 명확히 보강할 필요가 있습니다.

**더 짧게 말하면**

프로필 조건과 관심 이력은 맞춤 공고를 우선 보여주기 위한 신호로 사용합니다.

**주의할 표현**

“개인정보를 전혀 쓰지 않는다”, “개인정보 처리가 완벽하다”라고 말하지 않기.

## 4. 위험 표현 → 안전 표현

위험: 모든 정책 공고를 가져왔습니다.  
안전: 3개 공식 API 기준으로 통합했습니다.

위험: 신청 가능 여부를 AI가 판단합니다.  
안전: 관련 공고를 찾고, 최종 조건은 공식 원문 공고에서 확인하도록 연결합니다.

위험: 완전한 개인화 추천입니다.  
안전: 프로필 조건과 관심 이력을 참고해 관련 공고를 우선 보여주는 방식입니다.

위험: 실시간 자동 업데이트됩니다.  
안전: 자동 수집 구조는 준비되어 있고, MVP에서는 안정적인 검수와 반영을 우선했습니다.

위험: 챗봇이 정확한 신청 가능 여부를 알려줍니다.  
안전: 챗봇은 검색된 공고의 핵심 내용을 설명하고, 최종 확인은 원문 공고로 연결합니다.

위험: 중복 공고를 모두 제거했습니다.  
안전: 완전 중복과 처리하기 어려운 데이터는 줄였고, 기관·지역·상세 URL이 다른 유사 공고는 정보 손실을 막기 위해 유지했습니다.

위험: 검색 결과가 항상 정답입니다.  
안전: 검색 결과는 관련 공고를 찾기 위한 후보이며, 세부 조건은 원문 공고에서 확인하도록 연결합니다.
